# Grimoire V1.2 — Extração de Regras de Negócio — Design Spec

> Data: 2026-06-11 · Status: aprovado em brainstorming
> Extensão da V1.1 (ver specs anteriores). Regras de negócio com rastreabilidade `file:line`, extraídas pelo agente da sessão (agent-driven), persistidas e buscáveis.

## 1. Objetivo

Capturar regras de negócio do código ("desconto de 10% acima de 100", "CPF deve ter 11 dígitos") em linguagem natural, com rastreabilidade até a linha de origem, sem custo de API próprio e sem depender de recursos de cliente MCP.

## 2. Mudança de arquitetura vs spec V1.0

O spec V1.0 previa `extract_rules` via **MCP sampling** (LLM do cliente). Verificado em 2026-06-11:
- Claude Code **não suporta** sampling (anthropics/claude-code#1785)
- Sampling foi **deprecado na spec do MCP** (remoção anunciada em ~12 meses)

Decisão: **extração agent-driven** — o agente da sessão é o LLM. O server prepara candidatos e instruções; o agente extrai; o server valida e persiste. Custo de API zero para o projeto, funciona em qualquer cliente MCP, humano no loop naturalmente.

## 3. Decisões

| Decisão | Escolha | Racional |
|---|---|---|
| Mecanismo | Agent-driven, 2 tools (preparar + salvar) | Sampling morto; agente já pago pelo usuário; human-in-the-loop natural |
| Seleção de candidatos | Heurística de sinais de regra + paginação por cursor | Devolver tudo estoura contexto; heurística barata cobre o recall necessário |
| Staleness | Derivada: `file_digest` da regra ≠ digest atual do manifest ⇒ `stale=true` | Zero writes de manutenção; regras caras de extrair não são apagadas em edições |
| Arquivo deletado | Regras dele apagadas no sync | Sem alvo, sem regra |
| Busca | Regras espelhadas como chunks `kind="rule"` no índice + tool `rules()` de listagem | `search` existente encontra regra E código juntos; auditoria pela tool |
| Versão do índice | **Sem bump** (continua 2) | Tabela nova criada com `exist_ok=True` em índices existentes; schemas atuais intocados; regras sobrevivem a upgrades |
| Dedup | `id = sha256(file_path + rule_text)[:12]`; `save_rules` faz upsert por id | Re-extração idempotente |
| Versão do pacote | 0.3.0 | |

## 4. Tools

Todas com lazy sync e guard de path (`_rel_inside`) onde recebem `file_path`.

### 4.1 `extract_rules(project_path, scope=None, batch=10, cursor=0) -> dict`

- `scope`: prefixo de path (dir ou arquivo) ou `None` (projeto todo)
- Filtra chunks candidatos: `kind in {function, method, section}` cujo texto tem sinais de regra (regex única: condicionais `if/elif/else/switch/case/when`, `raise/throw/assert`, `validate/must/deve/limite`, comparadores `==/>=/<=/>/<`, `%`, literais numéricos em comparação); score = densidade de sinais; paths com `test` excluídos; ordenação determinística (score desc, file, start_line) para cursor estável
- Retorna:
  - `instructions`: prompt de extração para o agente — define o que é regra de negócio (comportamento observável do domínio, não detalhe de implementação), as categorias, confidence 0–1, o formato JSON e a ordem de chamar `save_rules`
  - `chunks`: lote de `{file, start_line, end_line, symbol, kind, text}` (`batch` itens a partir de `cursor`)
  - `next_cursor`: int ou null quando acabou; `remaining`: quantos candidatos faltam
- Não chama LLM nenhum; é puramente preparatório

### 4.2 `save_rules(project_path, rules: list[dict]) -> dict`

Cada regra: `{rule: str, category: str, file: str, start_line: int, end_line: int, confidence: float}`.

Validações (erro claro por item; itens válidos são salvos, inválidos retornam com motivo):
- `category` ∈ {validation, calculation, policy, workflow, other}
- `0 <= confidence <= 1`; `1 <= start_line <= end_line`; `rule` não-vazio
- `file` passa pelo guard de path e existe no manifest atual
- Persiste na tabela `rules` com `file_digest` atual do manifest e faz o espelho no índice de busca
- Retorna `{saved: [ids], rejected: [{rule, reason}]}`

### 4.3 `rules(project_path, file_path=None) -> list[dict]`

Lista regras (todas ou do arquivo): `{id, rule, category, confidence, file, start_line, end_line, stale}` — `stale` derivado na hora.

### 4.4 `delete_rule(project_path, rule_id) -> dict`

Remove da tabela `rules` e o chunk-espelho correspondente.

## 5. Armazenamento

### 5.1 Tabela `rules` (sem vetor)

`id, file_path, start_line int32, end_line int32, rule, category, confidence float32, file_digest`

### 5.2 Espelho no índice de busca

- Cada regra vira uma linha na tabela `chunks`: `kind="rule"`, `file_path` real da origem, `start_line/end_line` da regra, `symbol = "rule:" + id`, `text` = texto da regra (com prefixo marcador, ex: `[regra de negócio] ...`), vetor = embedding do texto da regra
- **Consistência no sync**: arquivo alterado ⇒ o delete-by-file existente remove também os rule-chunks; após re-indexar os chunks de código, o sync re-espelha as regras daquele arquivo a partir da tabela `rules`, acrescentando marcador de stale no texto (`[stale]`) já que o digest mudou
- Arquivo deletado ⇒ sync apaga as regras na tabela `rules` (e o delete-by-file já removeu os espelhos)
- `save_rules` substitui o espelho das regras que salvou (delete por `symbol` + re-add)

## 6. Tratamento de erros

- `extract_rules` com escopo sem candidatos ⇒ `{chunks: [], next_cursor: null, remaining: 0}` + instructions mesmo assim
- `save_rules` com lote parcialmente inválido ⇒ salva os válidos, rejeita os demais com motivo (agente corrige e re-tenta)
- `delete_rule` com id inexistente ⇒ `{deleted: false}`, não erro
- Espelho de busca falhando (embedding) não pode perder a regra: persistir na tabela `rules` primeiro, espelhar depois

## 7. Testes

- Heurística: chunk com validação/condicional é candidato; função utilitária pura sem sinais não é; paths de teste excluídos; paginação estável (cursor 0 → batch → next_cursor cobre tudo sem repetir)
- `save_rules`: válido salva; categoria inválida/confidence fora/linha invertida/arquivo inexistente rejeitam com motivo; upsert por id não duplica
- Staleness: salvar regra → editar arquivo → sync → `rules()` mostra `stale=true`; espelho re-emitido com marcador
- Cascata: deletar arquivo → regra some da tabela e da busca
- Busca: regra salva aparece em `search` com `kind="rule"` (query pelo texto da regra)
- `delete_rule` remove tabela + espelho
- Fluxo completo via `Client` in-memory simulando o agente: `extract_rules` → extrai manualmente do fixture → `save_rules` → `search`/`rules`
- Guard de traversal nas tools com `file_path`/`scope`

## 8. Não-objetivos (V1.2)

- Chamar LLM de qualquer forma (API direta ou sampling)
- Agrupamento de regras por domínio / geração de Gherkin (era fase 4 do pipeline antigo; fica para depois)
- Edição de regra (apagar + re-salvar cobre)
- UI de revisão — o cliente MCP é a interface
- Atualização da landing/ROADMAP fora do passo de release
